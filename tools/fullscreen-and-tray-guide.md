# Windows 多屏全屏遮罩、任务栏压制与托盘自愈工程指南

本文档沉淀自 **番茄钟（`pomodoro-timer v2.5.29 ~ v3.0.9`）** 与 **Blackout（`v1.2.0 ~ v1.2.1`）** 的实战开发与排障经验，供后续 Windows 桌面工具与全屏应用复用。

以下规则按当前实现与实际排障结果更新。历史方案与现行方案不一致时，以现行会话规则和专项证据为准；不把隔离测试、短时桌面采样或一次部署成功写成长期可靠性保证。文中版本含本地交付版本，不代表均已发布到 GitHub。

---

## 一、多屏全屏遮罩与任务栏、截图工具的共存边界

### 1. 常见踩坑与根因
1. **仅凭矩形坐标判断屏幕归属导致副屏任务栏闪烁**  
   在多屏紧邻或混合 DPI（如 `2880×1800@200%` 主屏 + `1200×1920` 副屏 + `3840×2160` 副屏）环境下，仅凭 `IntersectsWith` 或 `PtInRect(&mon_rect, center)` 会因边界擦边或 DPI 虚拟化偏移，将**未全屏副屏上的 DisplayFusion 任务栏（`DFTaskbar`）**误判为位于全屏屏幕内并调用 `ShowWindow(SW_HIDE)`。  
   当鼠标焦点切至副屏窗口时，DisplayFusion 检测到该屏活动窗口非全屏，立即调用 `SW_SHOW` 恢复任务栏，从而与全屏守护定时器的 `SW_HIDE` 形成 **300ms 周期的 `SW_HIDE` ↔ `SW_SHOW` 拉锯闪烁**。
2. **焦点离开全屏屏后放弃 `HWND_TOPMOST` 或移除 `EVENT_OBJECT_SHOW` 钩子**  
   - 若在焦点切到副屏时停止对全屏窗口执行 `SetWindowPos(HWND_TOPMOST)`，本屏任务栏会趁虚穿透全屏黑幕。
   - 若为规避截图冲突而完全移除 `EVENT_OBJECT_SHOW` 钩子，仅靠 300ms 定时器轮询，可能让任务栏直到下一次轮询才被隐藏；300ms 只是轮询间隔，实际呈现延迟还受调度、刷新率与消息处理影响。
3. **无白名单隐藏所有 `WS_EX_TOPMOST` 窗口导致截图画布被遮掉**
   QQ/微信截图（类名为 `TXGuiFoundation`）在启动时会创建跨所有显示器的置顶大画布。若不加类名白名单无差别隐藏置顶窗口，在未全屏的副屏上按 `Ctrl+Alt+A` 截图可能被 `SW_HIDE` 隐藏。这里是窗口被隐藏，不是截图进程被终止；具体延迟需要现场记录。

### 2. 屏幕归属、压制范围与层级保护
1. **用当前 `HMONITOR` 核对屏幕归属**
   压制任何任务栏前，必须调用 `MonitorFromWindow(hwnd, MONITOR_DEFAULTTONULL)` 获取目标窗口所属的物理显示器句柄，并与当前已开启全屏遮罩的显示器 `HMONITOR` 集合精确比对（`win_mon == item->handle`）。不属于全屏显示器的窗口应跳过；显示布局变化后重新枚举，不沿用失效的屏幕句柄。
2. **可压制窗口类名白名单（`is_suppressible_taskbar`）**  
   严格限定仅对以下类名执行 `SW_HIDE`：
   - `Shell_TrayWnd`（Windows 主屏原生任务栏）
   - `Shell_SecondaryTrayWnd`（Windows 副屏原生任务栏）
   - `DFTaskbar:` / `DisplayFusionTaskbar:` 根窗口（DisplayFusion 多屏任务栏）
   当前番茄钟不把 `Windows.UI.Core.CoreWindow` 纳入白名单；不能仅凭这个宽泛类名就压制系统窗口。不要触碰 `TXGuiFoundation`（QQ/微信截图）及其它用户置顶工具。
3. **`EVENT_OBJECT_SHOW` 双重门禁 + 保留保护对象的层级**
   - 全屏仍需维护层级，但不能无条件抢到所有窗口前面：有强提醒时排在提醒后面；有本软件操作窗口时排在操作窗口后面；无这些保护对象时才使用 `HWND_TOPMOST`。位置维护使用 `SWP_NOACTIVATE`，不借此改变焦点。
   - `SetWinEventHook(EVENT_OBJECT_SHOW)` 在回调中严格校验：
     ```c
     if (idObject != OBJID_WINDOW || idChild != CHILDID_SELF) return;
     if (event == EVENT_OBJECT_SHOW) {
         if (!hwnd || !fs_is_suppressible_taskbar(hwnd) || !fs_is_on_fullscreen_monitor_handle(hwnd)) return;
     }
     ```
     事件钩子用于缩短任务栏冒头到维护之间的延迟；定时器作为补充。不能仅凭有钩子就承诺 `<1ms` 或“零帧”，还需验证实际呈现和未选屏上的工具是否被干扰。

## 二、权限、自启与托盘恢复

### 1. 先区分项目，再判断权限需求

- 当前番茄钟清单为 `asInvoker`、`uiAccess=false`，不要求管理员权限，也没有 WMI/DDC/CI 亮度控制功能。Blackout 的亮度和管理员窗口经验不能直接当成番茄钟的已实现能力。
- 权限级别、消息传递、窗口层级和钩子能否收到输入是不同问题。遇到管理员窗口时，先验证失败的具体 API、完整性级别和返回结果，不能推断“只要管理员运行就一定能压住任何窗口或拦截任何按键”。
- 按任务所需选择最小权限，不为修复普通显示缺陷自动改成 `requireAdministrator`。执行级别含义参见[微软管理员权限说明](https://learn.microsoft.com/en-us/windows/win32/secbp/running-with-administrator-privileges)。

### 2. 自启与临时部署启动不是同一件事

当前番茄钟的开机自启使用 `HKCU\...\Run`；本轮交付使用临时 `schtasks /IT` 让新进程留在交互桌面，启动后删除任务。后者不等于创建或验证了持久开机自启，也不证明重新登录后的行为。

以下是长期常驻任务需核对的条件，不是所有任务都已设置或都需要更改的默认值：

| 条件 | 可能的影响 | 需要核对的配置 |
| :--- | :--- | :--- |
| `DisallowStartIfOnBatteries` | 电池供电时任务可能不启动 | 是否允许在电池供电时启动 |
| `StopIfGoingOnBatteries` | 切到电池供电后可能终止任务 | 是否允许常驻任务继续运行 |
| `ExecutionTimeLimit` | 达到配置时限后可能终止 | 常驻任务是否需要 `PT0S` |
| 用户和登录方式 | 进程可能不在可见交互桌面 | 用户账户、交互令牌和运行级别 |
| Explorer 登录期尚未就绪 | 首次托盘添加可能失败 | 异步补挂及 `TaskbarCreated` 恢复 |

需要提升权限的其他项目应显式设计 UAC 与任务运行账户，不依赖普通 Run 项静默取得提升权限；任务的运行级别参见[微软 RunLevel 文档](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-runlevel-principaltype-element)。

### 3. 托盘挂载与恢复的四道防线
1. **启动期绝不因首次 `Shell_NotifyIcon(NIM_ADD)` 失败而报错自杀**  
   首次 `NIM_ADD` 返回 `FALSE` 时，严禁弹窗退出（`return 1`），应启动异步重试定时器（如每 `1500ms` 重试一次 `NIM_MODIFY || NIM_ADD`），一旦托盘就绪立即挂载。
2. **运行期 `NIM_MODIFY` 失败自动回退 `NIM_ADD`**  
   在每次更新图标或心跳定时器中统一采用：
   ```c
   int published = Shell_NotifyIconW(NIM_MODIFY, &nid);
   if (!published) published = Shell_NotifyIconW(NIM_ADD, &nid);
   if (published) tray_cancel_retry(hwnd);
   else tray_schedule_retry(hwnd);
   ```
   不能忽略补挂 `NIM_ADD` 的返回值。重试与全屏刷新使用不同的主窗口定时器 ID；定时器 ID 只在对应窗口内区分，进出全屏不能取消补挂。当前主窗口补挂 ID 为 4007，全屏刷新为 4002。
3. **监听 `TaskbarCreated` 系统广播**  
   注册 `RegisterWindowMessageW(L"TaskbarCreated")`（高权限进程需配合 `ChangeWindowMessageFilterEx(..., MSGFLT_ALLOW, ...)` 放行跨 UIPI 消息），当 `explorer.exe` 崩溃重启时自动重新挂载托盘图标。
4. **已有实例唤醒与明确的升级流程**
   - 当前番茄钟用命名事件 `PomodoroTimerEvent` 识别已有实例，新进程向旧主窗口投递 `TaskbarCreated` 后退出；不是自动终止旧实例，也不是完整的无响应接管机制。
   - 不把“旧实例没响应”当成未经授权强杀的理由。升级时先核对目标进程和备份，再正常关闭旧版，确认退出后启动新版；仅释放单实例标识却让旧进程继续写数据，会引入双实例风险。

## 三、Win32 / .NET 桌面开发关键稳定性与体验细节

1. **P/Invoke 回调的引用寿命要覆盖原生使用寿命**
   `SetWindowsHookEx`、`SetWinEventHook` 等保留回调的调用，应在整个注册期间保留委托强引用，解除注册后再释放；静态字段、实例字段或合适的 `GCHandle` 都是选择，不必一律 `static readonly`。
   `EnumWindows`、`EnumDisplayMonitors` 等同步枚举不能与长驻钩子混为一谈：通过 P/Invoke 直接传入委托时，运行时在调用期间保护它；把委托转换为裸函数指针或留给原生代码延后使用时，要另行保证寿命。参见[微软回调封送说明](https://learn.microsoft.com/en-us/dotnet/framework/interop/marshalling-a-delegate-as-a-callback-method)和[原生互操作最佳实践](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/best-practices)。
2. **原生深色模式适配与右上方弹出托盘菜单**  
   - 历史 WinForms 托盘菜单曾出现左侧展开和主题不一致问题；具体行为取决于框架版本、系统主题与菜单对齐偏好，不能推断所有 `NotifyIcon.ContextMenuStrip` 都采用相同参数。当前番茄钟使用 `dark_mode.h` 的 Win32 菜单路径。
   - **本项目的原生菜单兼容实现**：
     1. **版本与导出检测**：
        - `uxtheme.dll` 序号导出属于非公开兼容实现，下面是本项目当前采用的版本分支，不是微软承诺未来不变的 ABI。应检查导出是否存在，失败时保留默认主题，不把版本门禁写成全系统兼容证明。
        - 当前代码在 Build 17763～18361 段按 `AllowDarkModeForApp(BOOL)` 调用序号 135，在 Build ≥18362 段按 `SetPreferredAppMode(PreferredAppMode)` 调用（参数 `APP_MODE_ALLOW_DARK`）；这是项目采用的兼容分支，不是未来系统的公开接口保证。
        - 当前实现通过 `RtlGetVersion` 获取 Build，避免依赖兼容性敏感的版本查询结果；Build < 17763 或查询失败时跳过这些序号调用。此处是代码分支核对，不代表已在所有旧系统实测。
     2. **初始化顺序**：
        - 当前启动流程先设 DPI 上下文，再初始化应用深色偏好，随后创建窗口；复用时保持这条经本项目采用的顺序，不把它扩大成所有主题缓存必然“锁死”的结论。
        - 窗口创建后显式调用序号 133 `AllowDarkModeForWindow(hwnd, TRUE)` 标记支持。
     3. **手写笔对齐保护与右上方稳定展开**：
        - 弹出前临时检测并执行 `SystemParametersInfoW(SPI_SETMENUDROPALIGNMENT, 0, NULL, 0)` 强制设为左对齐，再以 `TPM_LEFTALIGN | TPM_BOTTOMALIGN | TPM_RIGHTBUTTON | TPM_RETURNCMD` 调用 `TrackPopupMenuEx`，按既定方向展开菜单，并在屏幕边缘检查系统修正后的实际位置；菜单退出后还原原对齐值。这是临时修改系统参数的兼容措施，不能视为无副作用的通用方案；必须检查返回值、异常收尾和其他程序并发修改，优先考虑直接使用菜单定位参数而不修改全局偏好。
        - 本项目使用可作为菜单所有者的普通隐藏顶层窗口，不用仅消息窗口承担前台所有者角色。工具窗口样式是可选实现，不是所有应用唯一可用的样式。
     4. **收起后的消息投递与主题刷新**：
        - [微软托盘菜单示例](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-trackpopupmenu)在弹出前设所有者为前台窗口，返回后投递 `WM_NULL`，处理菜单重复显示时立即消失的问题。`WM_NULL` 本身[不执行操作](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-null)，不是排空、清除或处理完消息队列的命令。
        - 当前主窗口收到 `WM_SETTINGCHANGE` / `WM_THEMECHANGED` 时刷新菜单主题，弹出前也刷新；相关导出缺失时跳过。仍需核对目标系统的实际菜单外观，不承诺所有主题切换立即无感。
3. **`PerMonitorV2` 下无边框全屏窗口忌用 `FormWindowState.Maximized`**  
   在多屏混合 DPI 下，`Maximized` 容易被系统按主屏或 `WorkArea` 裁剪留边。应保持 `FormWindowState.Normal` + `FormBorderStyle.None`，直接通过 `EnumDisplayMonitors` + `GetMonitorInfo` 获取物理像素 `rcMonitor`，并用 `SetWindowPos` 精确覆盖。
4. **轻量无边框 Toast / 状态提醒条的防漂移与交互法则**  
   - **慎用 `WM_NCLBUTTONDOWN, HTCAPTION` 模拟拖动**：右下角自绘无边框通知弹窗若支持点击背景拖拽，极易在快速点击时发生误触漂移，导致弹窗脱离任务栏停靠区。
   - **折叠状态背景点击直达展开**：当通知弹窗超时或手动折叠为边缘极窄（如 40px）的垂直提醒条时，条形背景的点击事件应直接映射为展开命令，杜绝将窄条误拖到屏幕中央，大幅优化高频使用下的单手盲操体验。

## 四、Win32 桌面计时状态机：单线程消息驱动与单调时间

### 1. 痛点与历史教训
- **旧计时线程方案的风险**：早期版本使用独立工作线程（`timer_thread` 配合 `Sleep(1000)` 循环），通过投递自定义消息与主 UI 线程同步。在面对 Win32 复杂交互时暴露出三大硬伤：
  1. **模态消息循环阻塞**：当用户呼出输入框（`DialogBox` / `PromptForInteger`）、通用颜色对话框（`ChooseColor`）或系统右键菜单时，主线程进入模态消息泵。若设计成互相同步等待，容易发生滞后或死锁；模态循环本身仍处理部分消息，不能简单认为主线程完全停止；
  2. **时钟漂移与跳秒**：简单的 `Sleep(1000)` 在系统睡眠唤醒、锁屏或高频拖拽交互下无法真实反映单调物理时间流逝，极易产生累积漂移；
  3. **并发状态篡改**：微休息冻结/恢复、旧方案的超时刻度平移（现已移除）、快速托盘连击等多状态并存时，多线程共享状态必须加锁，极易引发死锁或状态覆盖。

### 2. 当前方案：主线程单调时钟与分段推进
1. **单调时间差与名义 50ms 心跳**：
   - 当前计时状态只由主窗口 UI 线程推进，不再由计时工作线程修改共享状态；这减少跨线程同步，不能消除模态消息重入、长任务阻塞或其他代码中的锁风险。
   - 通过 `SetTimer(hwnd, ID_TIMER_CLOCK, 50, NULL)` 驱动高频心跳，利用 `GetTickCount64() - timer_last_tick` 测量真实物理毫秒差值，累积转化为整秒推进，不能简单把每次 `WM_TIMER` 当成固定流逝 50ms。
   - `GetTickCount64` 通常只有 10～16ms 分辨率；`SetTimer` 的间隔也不是实时调度保证。这里适用于秒级番茄计时，不是高精度时钟。参见[微软 GetTickCount64 文档](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-gettickcount64)。
   - 不足一秒的活动余量要在暂停时保存、继续时接回；暂停时间不累计。新段与明确输入时间清余量，未截断的步进保留余量，截到边界则设准确边界。否则多次短暂停仍会丢秒。
2. **跨刻度分段步进推进（`timer_advance_seconds`）**：
   - 当系统睡眠唤醒、卡顿或长耗时事件发生导致单次累积时间大跨度增加（如一次性跳跃 900 秒）时，严禁直接执行 `remaining_seconds -= elapsed`。
   - 必须采用**分段步进推进算法**：以“下一个有效物理刻度（如微休息点）”切分推进区间。第一段步进至刻度边界并触发阶段流转（进入微休息等待）；剩余时间则作为新阶段流逝时间继续处理（如被动超时正计时），避免直接跨过刻度或丢掉后续阶段的流逝时间。系统睡眠是否计入流逝时间是独立产品规则，不可仅凭时钟选型宣称唤醒行为已实测。
3. **提醒代际与操作前同步**：
   - `timer_stage_generation` 标记真实阶段，到点事件携带代际号；处理时校验当前代际、提醒方式和已处理代际，关闭过的提醒不能因刷新或应用偏好补弹。
   - 执行主操作前同步单调时钟；已经自然到 0 的先按完成结算，不能因点击“结束”把完成误判成提前放弃。
   - 当前“修改时间”在弹窗前捕获代际，确认后同步时钟，再校验代际及 `timer_can_edit_time()`，变化时拒绝应用旧输入。其他输入需按其含义分别检查，不能由此推断所有模态输入都已经具有同样保障。

## 五、复杂桌面状态机设计的正交解耦法则（模式 / 状态 / 动作收敛）

### 1. 痛点：内部流程状态拼接与动词爆炸
- 随着复杂业务流程（番茄钟 ↔ 微休息 ↔ 超时正计时 ↔ 冻结恢复）叠加，容易犯“将内部流转状态直接拼接给用户看”的反模式（如“微休息完成 · 等待恢复专注 · 超时正计时”）；并在各入口随阶段动态发明大量动词（“恢复专注”、“下一阶段”、“开始微休息”、“继续自定义”）。
- **后果**：全屏 HUD、托盘悬停 Tooltip、会话菜单各说各话，视觉与心智模型极度混乱。

### 2. 现行状态机工程准则
1. **模式（Mode）与状态（State）严格正交分离**：
   - **Mode** 明确业务客体类型：`长番茄钟`、`短番茄钟`、`微休息`、`短休息`、`长休息`、`正计时`、`自定义计时`、`超时正计时`。
   - **State** 明确客体动静态：`待机`（未开始）、`运行`（无后缀）、`暂停`（已暂停）。
   - 严禁发明复合伪模式；全屏模式行、托盘悬停及弹窗状态文本遵循 `模式名 [ · 状态]`；不能把这条约束误套到按钮名称或数字图标。
2. **全局会话操作动词收敛为三原语**：
   - 会话控制仅保留基础动词：“开始”、“暂停／继续”、“结束”。
   - 会话菜单只有一个动态主操作，另有“暂停／继续”；菜单、托盘左键、弹窗按钮、普通全屏与强提醒右键共用主操作。
   - 待机显示“开始”，启动当前目标；普通运行或暂停显示“结束”，回到相应待机；所有超时（包括暂停后的超时）显示“开始”，一次直接运行下一模式。恢复暂停只通过“继续”。
   - 不因微休息链路再发明“恢复专注”“下一阶段”等按钮名称。
3. **瞬态提醒（Event）与驻留视图（View）彻底剥离**：
   - 完成是到点事件，不是长期占据画面的状态。提醒显示当前实际模式和统一操作，不再拼接“已完成／等待恢复”等额外状态。
   - 倒计时归零时：若开启超时正计时，无缝转入 `超时正计时` 模式；若关闭超时，直接显示下一阶段的 `待机` 状态（展示下一段的目标模式与预设/冻结时长）。画面所见即为点击“开始”将要启动的内容，消除“看着已完成、点击却开始新模式”的认知割裂。
4. **精确上下文冻结与接回模型（微休息生命周期）**：
   - 微休息触发时，立即精准冻结主番茄真实剩余秒数；微休息本身的倒计时与超时正计时完全独立，绝不消耗主番茄时间。
   - 到点未开始微休息时主番茄立即冻结，超时从零独立累加等待时长；原物理刻度保持不变，不保存“这个刻度已用过”的历史集合。
   - 40/15 的刻度是剩余 25、10 分钟。每次从刻度上方自然倒计时到刻度都产生新事件；触发后调回 26，再自然到 25，要再次提醒。直接设到刻度、手动跳过及恢复冻结值不原地触发，0 点完成番茄。
   - 恢复专注接回原冻结秒数；等待 20 或 35 分钟都不会延长主番茄或新增刻度。修改默认时长也不篡改冻结值。
5. **本轮快照与最小必要置灰**：
   - 当前方案是捕获本轮规则，不是把整个设置菜单锁住。微休息、超时、计数及长番茄计数配置可修改，本轮继续采用启动快照，新会话采用新值；暂停、微休息和恢复不是新会话。
   - 修改默认时长不改变运行中的倒计时上限。待机类型在准备时固定，预设时长可随对应设置更新；冻结番茄保留原类型和原秒数。
   - 只禁用当前确实不可执行的操作：待机、超时及微休息等待阶段不可改当前时间；自动折叠开关只在弹窗选项下可操作；真实运行时禁止导入和真实存储位置迁移。外观与音效可调，切换提醒方式只用于后续到点，选择关闭立即收起当前提醒。
   - 菜单置灰与命令执行共用 `timer_setting_locked()` / `timer_can_edit_time()` 等谓词。配置重复选择可点击但不重复写入；“重新准备待机”是主动放弃原上下文，不能当成普通重复配置选择。
6. **统计只按明确完成事件结算**：
   - 长番茄整段自然完成才记本轮配置数量；短番茄无论如何调时，自然完成只记 1；提前结束不记。正计时、休息、微休息、自定义和超时不计番茄。
   - 已有历史不重算。写入与提交失败要明确报告，不把半成功当作成功，也不能用无条件重试把同一次完成重复记数。

## 六、全屏 HUD 几何排版：基于关键分隔符的屏幕中心绝对锚定法则

### 1. 痛点：整体居中导致的动态水平抖动
- 在全屏大字 HUD 中，若对 `[模式名 · 状态]` 采取常规的整行水平居中，当计时器在运行态（无后缀）与暂停态（带“ · 已暂停”）之间切换时，由于整行字符串像素宽度剧烈改变，导致左侧的模式名在屏幕上左右晃动，破坏视觉稳定性与专注感。

### 2. 解决方案：中心字符绝对中轴对齐（`fs_status_layout`）
1. **以分隔符物理中心对齐屏幕横向中心**：
   - 包含分隔符（`·`）时，测量分隔符自身宽度 `dot_width`，将其绝对位置定死在 `X = ScreenCenter - dot_width / 2`。
   - 左侧模式名右对齐至分隔符左边距，右侧状态名左对齐至分隔符右边距，两侧间距严格对称；无分隔符时自动回退为整行常规居中。
2. **两侧最大外延（`half_extent`）与防溢出动态缩放**：
   - 计算两侧最大向外延伸尺寸：`half_extent = max(ScreenCenter - Left, Right + RightWidth - ScreenCenter)`。
   - 当 `half_extent` 超过屏幕安全可用宽度（如 `width * 0.4`）时，使用 `MulDiv(label_size, available, half_extent)` 动态按比例降级字号重算，以安全宽度约束布局并保持分隔符居中；最小字号、字体替换、超长文本及实际缩放仍需验证，不能承诺任意屏幕和任意文本都不越界。

## 七、Windows 桌面自动化测试工程化：系统全局 API 沙箱化与确定性隔离

### 1. 痛点与环境污染风险
- 涉及 Windows 托盘深色菜单、手写笔对齐（`SPI_SETMENUDROPALIGNMENT`）、全局输入钩子（`WH_MOUSE_LL` / `WH_KEYBOARD_LL`）的自动化测试，若直接在测试用例中调用真实 Windows API，会产生两大隐患：
  1. **污染宿主系统全局配置**：测试如果将系统手写笔对齐写入注册表/系统参数，会导致用户日常使用中所有软件的右键菜单都变成左撇子/右撇子异常对齐；
  2. **物理输入干扰导致测试偶发失败（Flaky Tests）**：自动化测试模拟合成拖拽与点击手势时，宿主机上真实的物理鼠标微小移动或按键会抢占全局钩子，导致合成状态机被打断。

### 2. 隔离测试与全局 API 旁路
1. **系统全局 API 模拟拦截（API Sandboxing）**：
   - 在测试框架中通过预编译宏将 `SystemParametersInfoW` 重定向至测试代理桩：
     ```c
     static BOOL WINAPI test_system_parameters(UINT action, UINT parameter, PVOID value, UINT flags) {
         if (action == SPI_SETMENUDROPALIGNMENT) return TRUE; /* 严禁自动化测试改动全局手写笔对齐 */
         return SystemParametersInfoW(action, parameter, value, flags);
     }
     #define SystemParametersInfoW test_system_parameters
     ```
   - 同样拦截 `TrackPopupMenuEx`，将模态菜单交互旁路化，测试直接通过分发 `WM_COMMAND` 校验逻辑，避免测试进程卡死在模态消息循环中。
2. **底层输入钩子直通（Hook Passthrough）**：
   - 拦截 `SetWindowsHookExW`：当测试注册低级鼠标/键盘钩子时，将其回调替换为只调用 `CallNextHookEx` 的无害直通桩，阻断外部物理桌面输入对内部合成手势状态机（`td.gesture`）的干扰。
3. **独立离屏虚拟桌面（Invisible Desktop Sandbox）**：
   - 测试启动时通过 `CreateDesktopW(L"PomodoroTestDesktop", ...)` 创建专属隐藏桌面，将测试线程通过 `SetThreadDesktop` 绑定至该桌面。
   - 所有全屏黑幕窗口、任务栏检测均在该虚拟桌面内创建与校验，不切换可见桌面，测试退出时统一销毁；隔离桌面不自动隔离文件、注册表和全局系统参数，仍需独立数据目录及相应 API 旁路。

## 八、v3.0.6～v3.0.7 排障教训与验收方法

v3.0.6 修复了强提醒层级竞争，但按目标 DPI 直接生成原尺寸图标的做法仍遗漏 20/24→16。v3.0.7 改用安全底图，并补齐辅助窗口保护和强提醒失败降级。以下记录 v3.0.7 实现；v3.0.8 的保护范围及事件维护见第九节，不把旧方案作为后续开发默认。

### 1. 黑闪要追踪中间层级，不能只看刷新后的结果

现象是强提醒白色阶段夹杂短暂黑闪。旧维护路径先把普通黑色全屏提到最前，再把强提醒提回来；最终顺序正确，中间状态仍可能呈现到屏幕上。新增追踪在每次原生窗口操作后检查顺序，旧路径单屏、双屏、三屏分别记录到 15、60、135 次中间违规。

修复要让普通全屏直接排在最下层提醒之后，同时覆盖定时维护、前台事件、首次创建、重新进入和主动激活。新全屏先在隐藏状态安排层级再显示。绘制读取同一次刷新提交的黑白阶段，不由每个窗口临时读取时钟决定颜色。

检查对象必须是可见窗口。把尚未显示的全屏窗口计入“遮挡”会产生假失败；反过来，只检查函数返回后的顺序又会漏掉真实的中间覆盖。短时可见桌面采样也要保留采样位置、阶段边界排除范围和异常结果，不能宣称无限时长无闪烁。

### 2. 全屏保护必须让本软件操作窗口可用

仅保护颜色／签名编辑器，会出现颜色能改、数字输入和统计却被遮住的割裂。要统一收集本进程在选屏上可见、未最小化的辅助窗口，保持原相对顺序，先保护辅助窗口，再把普通全屏排在它们后面。不得借此操作其他进程的窗口。

只保护定时刷新还不够：首次显示、已有操作窗时进入全屏、再次进入全屏、代码激活和原生 `WM_MOUSEACTIVATE` 都要检查。有操作窗口时，可用 `MA_NOACTIVATE` 保留点击投递而避免普通全屏抢激活；不能误用吃掉点击的返回值，使原点击动作失效。

临时置顶要有配对清理：记录窗口原先是否置顶，原先置顶的编辑器不能被误降级；最小化、移出选屏或退出最后一屏后恢复临时提升。标记放在窗口属性中，窗口销毁时随之清除，避免 HWND 被复用后错误恢复新窗口。层级调整使用 `SWP_NOACTIVATE`，不把恢复显示当成强行恢复旧焦点。

### 3. “没看见窗口”先区分隐藏、遮挡和启动标记

统计窗专项一度显示失败。诊断确认 `STARTUPINFO` 带 `STARTF_USESHOWWINDOW` 且 `wShowWindow=SW_HIDE`，首次 `ShowWindow(SW_SHOW)` 后窗口仍不可见，再显示才可见。根因不是窗口已经显示后又被全屏覆盖。

先记录 `IsWindowVisible`、`IsIconic`、窗口样式、矩形、进程与实际层级，再检查启动标记。用户明确打开统计时，首次显示未生效要补一次显式显示。首次显示前准备层级；显示消息中的后续维护投递到主窗口队列，避免递归调整正在显示的窗口。不要把未经证实的“递归导致隐藏”写成事故根因。

### 4. 字号通过不代表符号完整

上一轮只检查数字字号、原尺寸以及 32→16/24，仍漏掉了 20/24→16：`Ⅱ` 可只剩一条线，`+` 可缺一侧横臂。缓存和字号都正确，也不能代替最终像素检查；看到不完整的样图时，不能用“测试通过”否定图像。

当前底图尺寸为 `max(32, ceil(target_size / 16) * 16)`，使用可安全缩到 16 像素的整数网格；缓存仍包含实际目标尺寸。微休息前后等待的数字是主番茄冻结值，小 `Ⅱ` 表示等待；真正暂停使用大 `Ⅱ`，普通超时使用 `+` 和实际超时时长。低于一分钟的托盘数字按现有规则显示秒，悬停文本给出实际模式和完整时间。数字和前缀分别排版，最小完整笔画与可见间隙优先于死守约 40% 的字号比例。GDI 绘制结束后先 `GdiFlush()`，再直接设置 DIB alpha；不要用白色文字生成透明 AND 遮罩。

验收请求尺寸 16/20/24/32/40/48，各自绘制到最终 16/20/24/32；8 类文本共 192 组。检查两条独立竖线和间隙、加号双侧横臂与竖线、数字可辨认、背景遮罩及统计点。既输出原尺寸图，也实际查看样图。一次 Windows HICON 缩放检查不等同于第三方托盘的多次缩放或真实混合 DPI 布局实测。

### 5. 降级路径也必须走完生命周期

旧路径只在没有普通全屏时允许强提醒创建失败后弹窗；已有全屏时会同时没有强提醒和弹窗。故障注入应同时覆盖首个窗口失败与部分窗口失败，检查已建窗口完整清理后仍有可见降级提醒。

强提醒来源的降级弹窗不自动折叠，不被普通全屏或预览遮住，不因进入全屏或应用无关偏好消失。运行时记住提醒来源，不能一看到当前设置不是“弹窗”就无条件关闭已有降级弹窗。切换关闭立即收起；关闭不推进阶段；主按钮仍调用共享主操作。微休息前后两种等待都要验证冻结值与统计不变，同一到点不补弹，新事件重新提醒。

### 6. 证据分层与最小回归

| 检查 | 能支持的结论 | 不能替代的验证 |

## 九、v3.0.8 统计与窗口保护修复

### 1. 自动归档不能先追加再假设替换成功

旧归档路径超过 2 MB 后先追加月文件，再替换主日志，但未完整检查写入与替换结果。独立旧记录夹具中，真实锁定主文件阻止替换后重复执行，计数可由 1 变成 2、3；模拟月文件写入失败又可能造成记录丢失。v3.0.8 删除自动归档执行路径，新记录仍使用原事务式主日志提交，旧月文件继续读取、导入及导出。不得借此重算、去重、删除旧备份或 `.keep`；修复阻止新的损坏，不能推断历史数据已自动修好。

### 2. 黑白绘制与任务栏保护必须分开

强提醒每段只创建一次窗口，缓冲只随尺寸变化重建。黑白变化仅绘制；共享保护器覆盖普通全屏、预览及强提醒屏幕并集，250 ms 看门狗发现异常才维护层级。只识别系统任务栏和带冒号的 DisplayFusion 根任务栏，不能将任务栏缩略图和截图画布算进去。

任务栏隐藏失败不能记为成功隐藏。此次受限测试的原生调用返回 `ERROR_ACCESS_DENIED (5)`；必须在正常交互权限下复核，不能把权限受限产生的竞争当作正常运行结论。不要通过修改 DisplayFusion 配置、截图工具或全局系统设置回避测试。

仅主线程接收任务栏事件仍可能在绘制及消息处理时短暂泄漏。专用事件线程处理已确认隐藏的任务栏再次显示；目标快照带 HWND、PID 和根类名，用锁保护，覆盖收缩前撤销目标，最后一屏退出停止线程及全部钩子。新创建任务栏仍由共享保护器识别，不能无差别处理外部窗口。强提醒只覆盖一块屏幕、普通全屏覆盖另一块屏幕时，普通层还必须高于其本屏任务栏；仅检查它低于强提醒会遗漏跨屏任务栏插入。先修复强提醒锚点，再修复普通层与本屏任务栏的顺序，最后隐藏任务栏。

实机验收检查实际层级及任务栏区域合成像素，不能仅看 `IsWindowVisible`：逻辑可见而位于不透明全屏之后不等于闪烁。用户肉眼发现闪烁时，即使隔离测试通过，也不得宣布验收通过。各场景严格串行，每项至少十个黑白周期，保留失败与后续修复证据。

### 3. 辅助窗口与焦点边界

颜色、签名、数字输入及统计窗口共用临时置顶。以 `MonitorFromWindow(..., MONITOR_DEFAULTTONULL)` 的主要屏幕归属判断，仅主要位于普通全屏选屏时保护，少量跨屏接触不提升整窗。最小化、移到未选屏、退出对应全屏后撤销临时提升，不搬动窗口、不抢焦点。预览明确返回编辑器时仍恢复输入焦点和原选屏。应用关闭时必须直接销毁全部预览覆盖，不走返回原普通全屏的路径，否则可能残留任务栏保护；正常退出普通全屏也通过统一焦点恢复器尊重新的工作窗口。

显示器变更前后核对真实 `GetForegroundWindow()`，不把线程内 `GetFocus()` 当作全局用户选择。实际跨线程工作窗口的模拟移屏测试与物理拔插验收分开报告；新接入屏幕不扩张同一次提醒。

本轮专项为 `-SealOnly`、`-Interactive -GuardLive 0/1/2/3` 和 `-Interactive -FocusLive`，无关旧组不重跑。结果、部署哈希和未验证的物理边界写入本地验收记录。


## 十、v3.0.9 封版缺陷修复与工程实践经验

### 1. 五项封版缺陷的修复原则

1. **外部窗口 API 不能在保护快照锁内同步等待**：隐藏与恢复均由同一个工作线程异步提交，互斥锁只负责交换保护快照；必须严格区分“请求已受理”与“底层窗口已生效”。未执行完的隐藏也需排入恢复队列，快速退出重进必须继承恢复记录，绝不能在外部对象无响应时阻塞主线程。测试用慢窗口必须置于独立进程并显式指定与主程序相同的私有桌面，避免提前消耗人为设置的隐藏延迟。
2. **目录路径字符串不同不代表数据目录不同**：以跟随重解析点（Junction/Symlink）的目录真实句柄获取卷号和文件 ID，同源或身份不可确认时直接拒绝导入。先完整暂存全部白名单文件并逐字节校验，在原数据完成物理备份后方可执行清理与提交；空清单及枚举异常均视为失败。回滚操作必须尽力恢复所有原文件，禁止因单项清理失败而短路跳过后续文件恢复。
3. **模态窗口不会自动挡住外部消息**：每个数字输入框通过 `DialogBoxParam` 与 `DWLP_USER` 绑定独立栈上上下文；窗口标题、数值范围、默认值与输出结果严禁共享全局变量，彻底隔绝嵌套或并发对话框时的参数覆盖。
4. **统计不存在、读取失败与成功必须解耦**：全量临时聚合成功后方可替换全局显示快照，主日志、调整记录或月归档任一文件读取失败，均不得基于残缺基数写入目标调整。番茄钟完成事件的提交成功与界面显示刷新异步解耦；读回失败绝不代表提交未落盘，严禁自动二次兜底重记。
5. **恢复链必须逐项校验内容有效性**：临时配置或备份恢复主文件后，必须确认存在有效备份且内容语法合法；主文件和备份双重完整前必须保留恢复源。配置落盘必须走“独立临时文件写入 -> 完整性校验 -> 原子重命名替换”，提交与备份失败分开上报，不得把已落盘配置误判为失败。

### 2. 沙箱隔离桌面与实机交互（WinSta0\Default）挂载经验

在自动化 Agent、CI 或沙箱测试环境中，执行子进程默认被调度在隔离桌面（如 `exebox-...`）而非物理交互桌面 `WinSta0\Default`：
- **故障特征**：在带有 `-Interactive` 参数的实机验证脚本中，`FindWindowW` 无法查找到当前系统托盘、任务栏及 DisplayFusion 窗口，导致多屏压制实机测试无法正常挂载。
- **治理方案**：测试或运维工具在执行跨桌面窗口通信前，必须显式调用：
  ```c
  HWINSTA winsta = OpenWindowStationW(L"WinSta0", FALSE, MAXIMUM_ALLOWED);
  SetProcessWindowStation(winsta);
  HDESK desk = OpenDesktopW(L"Default", 0, FALSE, MAXIMUM_ALLOWED);
  SetThreadDesktop(desk);
  ```
  完成显式挂载后，方可正常枚举与定位物理交互桌面的顶层窗口句柄。

### 3. Windows 11 DWM 屏幕 DC 像素采样避坑实践

Windows 11 桌面窗口管理器（DWM）采用硬件加速合成渲染：
- **假阳性成因**：在 DWM 开启环境下，直接对 `GetDC(NULL)` 返回的屏幕设备上下文调用 `GetPixel(screenDC, x, y)` 会直接返回 `0xFFFFFFFF` (`CLR_INVALID`)。这曾导致实机测试误报 800+ 次“异常背景色（abnormal-background）”失败。
- **正确采样路径**：必须经由兼容内存 DC 与位图转发：
  ```c
  HDC memDC = CreateCompatibleDC(screenDC);
  HBITMAP bmp = CreateCompatibleBitmap(screenDC, 1, 1);
  HGDIOBJ old = SelectObject(memDC, bmp);
  BitBlt(memDC, 0, 0, 1, 1, screenDC, x, y, SRCCOPY);
  COLORREF pixel = GetPixel(memDC, 0, 0);
  SelectObject(memDC, old);
  DeleteObject(bmp);
  DeleteDC(memDC);
  ```
  经内存 DC 真实采样后，方可准确反映当前显示器上的真实合成像素。

### 4. 生产环境非破坏性部署与交互拉起规范

在向实际使用目录（如 `D:\pomodoro-timer\`）交付可执行文件时，严禁使用强制结束进程（`kill`）的方式更新：
- **PowerShell 线程约束**：PowerShell 主线程一旦触碰 UI 或控制台初始化，P/Invoke 调用 `SetThreadDesktop` 将抛出 `ERROR_BUSY` (170) 错误，因此复杂的跨桌面运维逻辑应采用干净的独立 Python 或 C 工具执行。
- **平滑停机与文件锁等待**：向旧实例发送 `WM_CLOSE` 触发其安全清理流程，循环轮询进程句柄直至退出；文件覆写需提供超时重试机制，以防御杀软或句柄延迟释放导致的瞬时权限异常。
- **交互式拉起**：部署后通过 `schtasks.exe /Create /TN ... /TR ... /IT` 交互式计划任务拉起，使程序自然依附于用户的当前物理会话，拉起完成后立即清理临时任务，不留系统垃圾。

### 5. 验收边界与物理热插拔规约

- **实机压制高密度采样**：DisplayFusion 任务栏压制改动直接影响视觉体验，必须在真实桌面上以严格串行方式依次执行 GuardLive 0（无全屏基准）、GuardLive 1（竖屏）、GuardLive 2（全屏组）、GuardLive 3（全屏预览），各场景完整测试 10+ 个黑白交替周期（单组采样点 > 1500 次），层级越界与异常背景数均为 0 方可判为通过。
- **严谨区分模拟与物理验证**：软件内重构或 `WM_DISPLAYCHANGE` 模拟不能替代物理显示器线缆插拔。受环境限制未执行物理插拔时，在验收报告与文档中必须如实记录为“缺省（环境限制未执行）”，严禁伪造通过结论。
- **发布控制**：本地部署更新与测试封版完成后，GitHub 远程推送与 Release 保持暂缓，严格等待明确指令。
